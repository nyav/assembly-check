# ocr-kylin-v11-Linux64_ctc.so · 拆视频取关键帧 · 经验笔记

> 来源：`github.com/nyav/ocr-kylin-v11-Linux64_ctc.so`（银河麒麟 V11 + RTX 3060 OCR 实测展示仓库）
> 做法核心：**拆视频 → 取关键帧 → 挑出各类动作的实机截图 → 编号配图展示**（README 里放 01~05 编号实机截图 + 指标表 + 封面）。
> 落地示例：从装配检查录屏拆出 4 张实机截图（外观检查-顶端 / 铜体 / 装白色堵头 / 装配完成），嵌入文章页并推入 GitHub 仓库。

---

## 一、一句话理解这套做法

> **把现场录屏当成"证据素材"：拆帧 → 按需定位各类动作的关键帧 → 抽出干净实机截图 → 编号配图（01/02/03…）+ 指标表 + 封面，用于展示与发布。**

它不是"随便截几帧"，而是**有目的地取**：每一张都要对应一个可辨识的动作/状态，且要在图中能"看得到证据"（如检测框、红字类别标签、日志）。

## 二、展示层的"实机截图"范式（OCR 仓库 README 的做法）

OCR 仓库 README 的结构，是这套做法的最终落地形态：

1. **封面图**（横版 cover-16x9 + 竖版 cover-9x16）
2. **指标表**：一行一个实测值（吞吐 302 张/秒、3ms、99.0%、14 路并发…），都是真实测得
3. **01~05 编号实机运行截图**：每张配一句说明，全部"实机录制，非效果图"
   - 01 部署环境 → 02 启动加载 → 03 并发推理 → 04 识别结果 → 05 指标汇总
4. **适用场景 + 全栈自主可控说明**

> 关键纪律：**图必须是真实运行画面**（界面/日志/检测框清晰可见），文字只写实测值、不改数据。这就是"实机截图"和"效果图"的区别，也是可信度所在。

## 三、拆视频取关键帧的实操步骤（装配检查落地版）

### 0. 探针视频（先摸清素材）
```
ffmpeg -hide_banner -i <video>   # 看 Duration / 分辨率 / 帧率
```
装配检查源视频实测：51.02s · 1318×598 · 24.7fps（与检测日志写的 1920×1080 不一致，以实际为准）。

### 1. 按 1fps 拆帧，建立全集
```
ffmpeg -y -i <video> -vf "fps=1" out\f_%03d.jpg   # 51s → 51 帧
```

### 2. 拼接触表（PIL），一次性定位
- 先拼**全帧接触表**看整体节奏；
- 若目标（红字叠加）太小，再拼**裁到目标区域的放大接触表**（本例裁左侧视频区 40,60,660,560）。
- 每格标时间，一次读 51 帧，比逐帧读高效。

### 3. 读帧判定"当前激活类别"
装配检查的界面里，**当前检测类别以红色文字叠加在左侧视频上**（如「0=外观检查-顶端」「2=装白色堵头」），右栏是静态动作列表（别被它干扰）。用接触表读出每帧的叠加类别 → 得到动作循环序列。

### 4. 为每类动作挑"干净代表帧"
- 装配检查呈现稳定循环：**0 顶端外观 → 1 铜体外观 → 2 装堵头 → 4 装配完成**
- 每类选一帧**叠加标签清晰、画面不处于动作切换瞬间**的代表帧。
- 实测代表帧：t=9s(0)、t=14s(1)、t=22s(2)、t=5s/24s(4)。

### 5. 用 `-ss` 抽整幅关键帧
```
ffmpeg -y -ss <秒> -i <video> -frames:v 1 out\01_外观检查_顶端.jpg
```
`-frames:v 1` 只取一帧；文件名语义化命名。

### 6. 逐张核对（读帧确认叠加类别）
抽取后逐张 Read 核对红字叠加确实是目标类别；不对就换候选帧（动作循环快时，做密集扫描：`@(3,4,5,6,23,…)` 批量抽，再拼小接触表一次挑）。

### 7. 编号配图 + 上传/嵌入
- 编号命名：`01_外观检查_顶端` / `02_外观检查_铜体` / `03_装白色堵头` / `04_白色堵头装配完成`
- 嵌入文章页成"实机运行截图 · 四类装配动作"2×2 卡片区，配一句话说明
- 推入 GitHub 仓库 `images/` 并随页面上线

## 四、工具链（本机实测可用）

| 用途 | 命令/路径 |
|---|---|
| ffmpeg | `C:\Program Files (x86)\FormatFactory\ffmpeg.exe` |
| 拆帧 | `ffmpeg -i <v> -vf "fps=1" f_%03d.jpg` |
| 抽单帧 | `ffmpeg -ss <秒> -i <v> -frames:v 1 out.jpg` |
| 拼接触表 | Python + PIL（用 `sandbox_runtime\bases\…\python\python.exe`，默认 `python` 无 PIL） |

## 五、踩坑记录

| 坑 | 现象 | 解法 |
|---|---|---|
| 默认 `python` 无 PIL | `ModuleNotFoundError: No module named 'PIL'` | 用 `sandbox_runtime\bases\d0ace…\python\python.exe` |
| OCR 对视频上的红字叠加检测不稳定 | 同帧时读到、时读不到叠加 | 裁目标区域放大再读；多看几帧取交集 |
| 动作循环太快 | 单帧停在动作切换瞬间，类别不清 | 密集抽帧（0.5~1s 一档）+ 小接触表一次挑 |
| 某些类别全程未触发 | 装配检查类别 3「放说明书」6701 帧一次没出现 | 不硬凑图，展示里标注"可选接入工位"，避免误导 |
| 抽出的帧对不上预期类别 | `-ss 38` 抽出却是「2=」 | 以抽帧后逐张核对为准，别只信接触表估的时间 |
| 界面静态动作列表干扰判定 | 误把右栏列表当成当前类别 | 只看**视频上的红字叠加**，列表只当参照 |

## 六、这套做法的通用价值

- **证据式展示**：实机截图让"系统真的在跑"变得可证，比纯文字/效果图更有说服力
- **可复用**：任何有检测界面/日志的录屏，都能用同一套拆帧→定位→挑代表帧→编号配图的流程
- **落地场景**：演示视频关键帧、仓库 README 配图、公众号配图、宣传片素材、缺陷/动作证据归档

> 结论：**拆视频取关键帧的核心不是"会拆"，而是"会挑"——每张图都要对应一个可辨识、可标注、真实发生的状态，再按编号配图展示。**
